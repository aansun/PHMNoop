# NOOP Live Activity Audio & Coaching Engine
## Implementation Blueprint for Codex

**Document type:** Engineering implementation blueprint
**Target project:** NOOP fork
**Primary platforms:** iOS first; Android parity later
**Architecture inspiration:** Garmin Activity Engine + Activity Prompts
**Design principle:** Local-first, deterministic-first, device-agnostic

---

## 1. Objective

Implement a modular live activity audio system in the NOOP fork that can:

1. Consume live metrics from WHOOP and future sources.
2. Maintain a reliable activity/workout state.
3. Detect meaningful activity events.
4. Convert events into prioritized activity prompts.
5. Speak prompts through native offline TTS.
6. Coexist cleanly with music/podcasts using audio ducking.
7. Optionally enrich selected coaching prompts with AI.
8. Remain extensible to Garmin, HealthKit, Bluetooth HRMs, and Android.

The core architecture MUST separate:

```text
Sensor Data
    ↓
Live Metric Bus
    ↓
Activity Engine
    ↓
Activity Event
    ↓
Prompt Engine
    ↓
Activity Prompt
    ↓
Prompt Scheduler
    ↓
Audio Engine
    ↓
Headphones / Speaker
```

AI MUST NOT be required for basic activity detection, workout execution, safety/threshold logic, or prompt scheduling.

---

## 2. Non-Goals for V1

Do NOT make V1 dependent on:

- Cloud LLM calls
- Cloud TTS
- Garmin Connect
- Garmin ActivityPrompts API
- Apple Health synchronization latency
- Continuous AI inference
- Medical/safety diagnosis
- Arbitrary streaming audio generated by an LLM

V1 should work offline with WHOOP live data and native platform TTS.

---

## 3. Architectural Principles

### 3.1 Device-Agnostic Core

The Activity Engine must never know whether metrics originated from:

- WHOOP
- Garmin
- Apple Watch / HealthKit
- Bluetooth HRM
- Phone GPS
- Simulator

Normalize all sensor data before it reaches the Activity Engine.

### 3.2 Events, Not Sentences

The Activity Engine emits structured events.

BAD:

```text
HR > target → "Your heart rate is too high."
```

GOOD:

```text
HR > target
    ↓
ActivityEvent.heartRateAboveTarget
    ↓
PromptEngine
    ↓
ActivityPrompt
```

### 3.3 Deterministic First

Rules decide **whether and when** coaching is needed.

AI may decide **how selected non-critical coaching guidance is worded**.

```text
Rules decide WHEN.
AI may decide HOW TO SAY IT.
```

### 3.4 Local-First

Prefer:

- local computation
- local persistence
- native TTS
- deterministic templates
- offline operation

Network connectivity must not be required for normal activity prompts.

# 6. Sensor Abstraction

Create a common interface for live activity sources.

```swift
protocol ActivityMetricSource {
    func start() async throws
    func stop() async

    var metrics: AsyncStream<LiveMetrics> { get }
}
```

Expected implementations:

```text
ActivityMetricSource
        ▲
        │
 ┌──────┼─────────┬────────────┐
 │      │         │            │
WHOOP  Garmin  HealthKit   Demo/Replay
```

Garmin support is a future adapter and MUST NOT be required by the core engine.

---

# 7. LiveMetrics

Use a normalized model.

```swift
struct LiveMetrics: Sendable {
    let timestamp: Date

    let heartRate: Int?
    let heartRateZone: Int?

    let paceSecondsPerKm: Double?
    let speedMetersPerSecond: Double?
    let cadence: Int?

    let distanceMeters: Double?
    let elevationMeters: Double?

    let calories: Double?

    let latitude: Double?
    let longitude: Double?
    let gpsAccuracyMeters: Double?
}
```

Rules:

- Missing data must be represented as `nil`.
- Do not fabricate unavailable metrics.
- Include timestamps for stale-data detection.
- Normalize units before publishing.
- Prefer monotonic/session clocks internally for duration-sensitive rules.

---

# 8. Live Metric Bus

Responsibilities:

- Receive normalized metric samples.
- Maintain latest known metric state.
- Publish updates to ActivityEngine.
- Detect stale sources.
- Merge compatible sources where appropriate.
- Avoid coupling UI to BLE callbacks.

Concept:

```text
WHOOP BLE ──┐
GPS ────────┼──→ MetricNormalizer → LiveMetricBus → ActivityEngine
HealthKit ──┘
```

The bus should support AsyncStream/actors or another concurrency-safe equivalent.

---

# 9. Activity State Machine

Use explicit state.

```swift
enum ActivityState {
    case idle
    case preparing
    case active
    case paused
    case ending
    case completed
}
```

Transitions:

```text
IDLE
 ↓
PREPARING
 ↓
ACTIVE ─────────→ PAUSED
 ↑                  │
 └──────────────────┘
 ↓
ENDING
 ↓
COMPLETED
```

State transitions should emit events.

Examples:

```text
preparing → active
= activityStarted

active → paused
= activityPaused

paused → active
= activityResumed

active → ending
= activityEnding
```

Do not derive all behavior from a single `isWorkout` boolean.

# 10. ActivityEvent Model

The Activity Engine outputs events, not speech.

Recommended initial events:

```swift
enum ActivityEvent: Sendable {
    case activityStarted
    case activityPaused
    case activityResumed
    case activityEnded

    case lapCompleted(LapSummary)
    case distanceMilestone(meters: Double)

    case heartRateZoneEntered(zone: Int)
    case heartRateAboveTarget(current: Int, targetMax: Int)
    case heartRateBelowTarget(current: Int, targetMin: Int)
    case heartRateReturnedToTarget

    case paceAboveTarget
    case paceBelowTarget
    case paceReturnedToTarget

    case workoutStepStarted(WorkoutStep)
    case workoutStepEnding(step: WorkoutStep, secondsRemaining: Int)
    case workoutStepCompleted(WorkoutStep)

    case highExertion
    case recoverySuggested
}
```

Events must include enough context to generate prompts without re-reading unstable global state.

# 11. HR Zone Engine

V1 must support heart-rate-zone events.

The exact zone calculation should remain configurable and independent from the audio layer.

Possible input:

```text
current HR
configured HR zones
workout target zone
```

Possible output:

```text
zone entered
above target
below target
returned to target
```

Do not fire prompts directly from raw HR changes.

---

# 12. Hysteresis

Hysteresis is mandatory.

Example target:

```text
Target HR = 135–145 bpm
```

Bad raw samples:

```text
144
146
145
147
144
146
```

must NOT produce repeated alerts.

Recommended conceptual rule:

```text
Upper target: 145

Trigger threshold:
HR > 150

Trigger duration:
20 seconds

Recovery threshold:
HR <= 145

Recovery duration:
15 seconds
```

State:

```text
NORMAL
   │ sustained violation
   ▼
ABOVE_TARGET
   │ sustained recovery
   ▼
NORMAL
```

Configuration should support:

```swift
struct ThresholdRule {
    let triggerValue: Double
    let triggerDuration: TimeInterval

    let recoveryValue: Double
    let recoveryDuration: TimeInterval
}
```

Never use a single instantaneous sample for routine coaching alerts.

---

# 13. Trend Engine

Do not evaluate only the current sample.

Maintain rolling trends such as:

```text
HR 30 seconds
HR 2 minutes
Pace 30 seconds
Pace 2 minutes
Cadence
```

Example output:

```swift
struct MetricTrends {
    let hr30sDelta: Double?
    let hr2mDelta: Double?
    let pace30sDelta: Double?
    let pace2mDelta: Double?
}
```

This enables future coaching such as:

```text
pace stable
+
HR rising continuously
=
possible HR drift
```

# 14. WorkoutContext

Create a snapshot representing the session context.

```swift
struct WorkoutContext: Sendable {
    let activityType: ActivityType
    let state: ActivityState

    let duration: TimeInterval

    let metrics: LiveMetrics
    let trends: MetricTrends

    let targetHeartRate: ClosedRange<Int>?
    let targetPaceSecondsPerKm: ClosedRange<Double>?

    let currentStep: WorkoutStep?

    let recoveryScore: Int?
    let sleepScore: Int?
    let restingHeartRate: Int?
    let hrv: Double?
    let strain: Double?

    let lastPrompt: ActivityPrompt?
}
```

Important:

Historical/recovery data is contextual input.

It should not silently redefine explicit workout targets unless product requirements explicitly define that behavior.

# 15. Prompt Engine

The Prompt Engine answers:

```text
"Given this ActivityEvent and current context,
should the user hear something?"
```

Pipeline:

```text
ActivityEvent
      ↓
PromptPolicy
      ↓
Cooldown
      ↓
Deduplication
      ↓
Priority
      ↓
PromptCandidate
```

It must NOT own audio playback.

# 16. Prompt Model

Use a Garmin-inspired structured prompt.

```swift
struct ActivityPrompt: Identifiable, Sendable {
    let id: UUID

    let templateName: String
    let text: String

    let context: PromptContext

    let priority: PromptPriority

    let createdAt: Date
    let expiresAt: Date?

    let source: PromptSource
    let interruptPolicy: InterruptPolicy
}
```

Suggested source:

```swift
enum PromptSource {
    case system
    case workout
    case activityRule
    case aiCoach
    case garminBridge
}
```

Suggested interrupt policy:

```swift
enum InterruptPolicy {
    case never
    case lowerPriorityOnly
    case always
}
```

# 17. Prompt Priority

Use stable numeric priorities.

Lower number = higher priority.

```text
0   CRITICAL
10  WORKOUT_TRANSITION
20  TARGET_ALERT
30  LAP
40  COACHING
50  INFORMATION
60  MOTIVATION
```

Example:

```swift
enum PromptPriority: Int, Comparable {
    case critical = 0
    case workoutTransition = 10
    case targetAlert = 20
    case lap = 30
    case coaching = 40
    case information = 50
    case motivation = 60
}
```

Do not treat motivational speech as equal priority to workout transitions.

# 19. Template Prompt Engine

V1 should use deterministic templates.

Examples:

```text
activity.started
"Workout started."

activity.paused
"Workout paused."

lap.completed
"Lap {lap}. Average pace {pace}."

hr.above_target
"Heart rate {heartRate}. Above target zone."

hr.returned_to_target
"Heart rate back in target zone."

workout.step.started
"Next interval. {duration}. Target {target}."
```

Requirements:

- Templates must support localization.
- Keep spoken text concise.
- Do not include unnecessary units repeatedly.
- Avoid long sentences during high-intensity activity.
- Template rendering must be testable without an audio device.

---

# 20. Prompt Deduplication

Repeated events must not cause repeated speech.

Generate a semantic fingerprint.

Examples:

```text
HR_ABOVE_TARGET_ZONE_3
PACE_BELOW_TARGET_STEP_4
LAP_COMPLETED_5
```

Maintain last-spoken time by fingerprint.

Example policy:

```text
same target alert:
120 sec cooldown

lap:
no duplicate for same lap ID

workout transition:
unique per transition

motivation:
minimum several minutes
```

Do not use only text equality because localized/AI text may differ while representing the same event.

---

# 21. Prompt Expiration

Prompts may become irrelevant while waiting in the queue.

Example:

```text
AI:
"You're holding a steady pace."
```

If a workout interval transition occurs before it is spoken, the coaching prompt may no longer be useful.

Support:

```swift
expiresAt: Date?
```

Scheduler must discard expired prompts.

Suggested examples:

```text
Workout transition: long/controlled lifetime
Target warning: short lifetime
Lap: moderate lifetime
AI coaching: ~5–15 seconds
Motivation: short lifetime
```

Tune values through testing rather than hard-coding product assumptions permanently.

---

# 22. Prompt Scheduler

Never call TTS directly from PromptEngine.

Use:

```text
PromptEngine
     ↓
PromptScheduler
     ↓
PriorityQueue
     ↓
AudioEngine
```

Responsibilities:

- Priority queue
- Expiration
- Deduplication
- Minimum interval
- Interrupt handling
- Current-speaking state
- Queue cleanup

Example simultaneous prompts:

```text
P10 Workout:
"Recovery interval."

P30 Lap:
"Kilometer five."

P40 AI:
"You're maintaining good rhythm."
```

Expected order:

```text
P10
 ↓
P30
 ↓
P40 only if still relevant
```

# 24. Audio Ducking

The application should not manually stop and restart Spotify/Apple Music for every prompt.

Desired behavior:

```text
Music
████████████████████

Prompt begins

Music
████░░░░░░░░░░████

"Heart rate 151.
Reduce your pace slightly."

Music
████████████████████
```

Use platform audio-session mixing/ducking where appropriate.

Test:

- AirPods
- generic Bluetooth earbuds
- iPhone speaker
- music playing
- podcast playing
- incoming call
- Siri interruption
- headphones disconnected during speech

# 25. Audio Route Behavior

AudioEngine should observe route changes.

Examples:

```text
AirPods connected
→ use current system route

AirPods disconnected
→ apply configured speaker fallback policy

Bluetooth route changes
→ do not crash or lose scheduler state
```

Do not hard-code AirPods as the only supported output.

# 27. AI Coach Architecture

AI is an optional contextual wording layer.

Correct:

```text
Metrics
  ↓
ActivityEngine
  ↓
Deterministic Coaching Rules
  ↓
Is coaching useful?
  │
  ├── NO → silence
  │
  └── YES
       ↓
Context Builder
       ↓
AI wording
       ↓
Prompt Scheduler
```

Incorrect:

```text
Every HR sample
   ↓
LLM
   ↓
"Should I say something?"
```

Do not invoke an LLM continuously.

# 28. Coaching Rule Engine

Examples of future deterministic coaching triggers:

```text
HR drift:
HR increasing over 2 min
+
pace approximately stable
+
target = aerobic
+
sustained condition

Pace deterioration:
pace slower than target
+
HR not limiting
+
sustained condition

Recovery-aware effort:
low recovery context
+
unexpected HR response
+
non-interval activity
```

Rules should generate semantic coaching intents.

Example:

```swift
enum CoachingIntent {
    case reduceEffort
    case increaseEffort
    case stabilizePace
    case recover
    case maintainCurrentEffort
}
```

AI receives the intent; AI does not invent the underlying trigger.

# 29. AI Context

Only send necessary structured context.

Example:

```json
{
  "activity": "running",
  "duration_min": 35,
  "heart_rate": 158,
  "target_hr": [135, 145],
  "pace": "7:10/km",

  "hr_trend_bpm": 9,
```

AI output constraints:

- one short spoken instruction
- no diagnosis
- no unsupported safety claims
- no invented sensor values
- no markdown
- no lengthy explanation

# 33. Safety Boundary

NOOP is not a medical device.

Do not implement logic such as:

```text
metrics → LLM → diagnose dangerous condition
```

Instead:

```text
configured deterministic rule
        ↓
activity notification/coaching intent
        ↓
optional wording layer
```

Use conservative language for health-related prompts.

Examples:

Preferred:

```text
"Your heart rate is above your workout target."
```

Avoid:

```text
"Your heart rate is dangerously high."
```

unless a separately validated product requirement supports such a statement.

# 38. Performance Targets

Initial engineering targets, to validate empirically:

```text
Metric → ActivityEvent:
< 250 ms after rule condition becomes satisfied

ActivityEvent → queued deterministic prompt:
< 100 ms

Native TTS start:
as fast as platform permits

UI dependency:
none

Cloud dependency for V1:
none
```

Do not optimize raw sensor-to-audio latency by removing hysteresis/sustained-condition protections.

# 43. Definition of Done — V1

V1 is complete when all of the following are true:

1. A WHOOP live activity can feed HR into ActivityEngine.
2. ActivityEngine operates while the workout screen is not visible.
3. HR threshold logic includes duration + hysteresis.
4. A short HR spike produces no alert.
5. A sustained target violation produces exactly one appropriate prompt.
6. Returning to target can generate a recovery prompt according to policy.
7. Lap/distance prompts work.
8. Workout-transition prompts have higher priority than informational prompts.
9. Repeated events do not create speech spam.
10. Expired prompts are discarded.
11. Audio can play through the active iOS audio route.
12. Music/podcasts are ducked rather than manually stopped where supported.
13. Bluetooth route changes are handled.
14. Incoming audio interruptions do not corrupt the queue.
15. Native TTS works without network access.
16. All core rule/scheduler behavior has automated tests.
17. Recorded activity data can be replayed through the engine.
18. AI is not required for any V1 feature.

## Codex Implementation Instruction

When implementing this blueprint:

1. Inspect the existing NOOP architecture before creating new modules.
2. Reuse existing BLE, storage, analytics, and background infrastructure.
3. Avoid duplicating existing models/services.
4. Keep core engines independently testable.
5. Prefer protocol-driven dependency injection.
6. Add tests with each engine rather than after implementation.
7. Do not introduce cloud dependencies into V1.
8. Do not implement AI until the deterministic activity/prompt/audio pipeline passes tests.
9. Preserve existing NOOP behavior unless explicitly required to change it.
10. Make incremental commits/features so regressions can be isolated.

The intended result is not a Garmin clone.

The intended result is a **device-agnostic NOOP Activity Intelligence layer** inspired by Garmin's separation of activity events, activity prompts, priorities, and audio delivery, while leveraging NOOP's local health/recovery context for future intelligent coaching.
